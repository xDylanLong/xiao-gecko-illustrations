# 小Gecko认知模型库

这份库把常见模型变成可复用的手绘解释骨架。模型不是画面装饰，也不是把逐字稿塞进框里；先确认口播需要的认知关系，再选择最小的模型。

## 名称显示规范

每张模型图都要在顶部居中或白板标题区显示标准模型名称，并与主题标题分开：

```text
问题树｜示意框架
内容项目为什么推进不动？
```

图表使用同样的规则：`饼图｜示意数据`、`折线图｜示意数据`、`柱状图｜示意数据`。名称是帮助观众识别结构的专业标签，不是左上角的技术分类，也不能遮挡节点、坐标轴、图例或关键结论。

## 使用规则

### 先选认知任务

| 口播要回答的问题 | 首选模型 | 视觉骨架 |
|---|---|---|
| 这个问题由哪些部分组成？ | 问题树 / 5W1H | 树根、枝条或问题卡片 |
| 为什么会发生？ | 5 Whys / 因果链 | 向下追问或向右传递 |
| 哪个因素会造成什么结果？ | 因果链 / 因果回路 | 节点、箭头和反馈环 |
| 接下来应该怎么选？ | 决策树 | 判断门、岔路和结果 |
| 哪个对象更值得优先处理？ | 2×2 矩阵 | 两条轴和四个区域 |
| 一个概念由什么组成？ | Why–What–How / 分层模型 | 三层关系或阶梯 |
| 一个方法如何持续改进？ | PDCA | 闭环四步 |
| 内外部条件分别是什么？ | SWOT | 四个区域，两组边界 |
| 多个角色或模块如何互相影响？ | 系统关系图 | 节点、输入、阻力和反馈 |
| 用户或事情如何经历不同阶段？ | 用户旅程 / 时间线 | 路线、触点和转折 |

### 模型保真度

- **标准结构**：用户点名模型，保留公认组成、顺序、轴、分支或循环。模型名可以出现，但不要添加用户没有提供的事实。
- **内容适配结构**：用户没有点名模型，只需要一个专业的表达方式。保留模型的逻辑骨架，用当前内容替换节点。
- **示意框架**：内容只有假设、例子或大概关系。保留结构，不把推测包装成验证过的结论，并在画面中写“示意框架”或“示意关系”。

默认每张图使用 3-6 个核心节点。超过 6 个节点时，拆成“总览 + 局部”或多张连续素材；不要为了完整而牺牲可读性。

## 问题拆解

### 问题树 / MECE 风格拆解

- 用于从一个结果、症状或大问题向下拆出原因、子问题或工作包。
- 骨架：根问题 → 2-4 个一级分支 → 必要时每个分支 1-2 个子节点。
- 画面：纸树、地下根系、抽屉柜或分叉管道；小睫毛挖根、拉开枝条或给关键分支做标记。
- 约束：只有在内容确实支持时才暗示“互不重叠、覆盖完整”；普通示意图不要把“MECE”当作已验证结论。

### 5 Whys

- 用于沿着一个具体问题逐层追问“为什么”，寻找可行动的根因。
- 骨架：现象 → 为什么1 → 为什么2 → … → 可行动根因。
- 画面：向下的井、连续房门或一串被打开的抽屉；小睫毛逐层下探。
- 约束：不机械凑满五层；如果第三层已经得到可行动根因，就在那里停下并标记“当前根因”。

### 5W1H

- 用于把一个模糊任务补齐为对象、目的、时间、地点、参与者和方法。
- 骨架：What / Why / Who / When / Where / How；只保留对当前任务有用的 3-6 项。
- 画面：一张调查板、六个抽屉或一只被逐项打开的行李箱；小睫毛把模糊问题拆成短卡片。
- 约束：不是固定六宫格；缺少的信息写“待确认”，不要自行补造。

## 因果与循环

### 因果链

- 用于解释触发条件、关键机制和最终结果。
- 骨架：原因 → 中间机制 → 直接结果 → 可观察后果；3-6 个节点。
- 画面：齿轮、管道、接力棒或一串骨牌；小睫毛传递、卡住或修补其中一个环节。
- 约束：箭头只表示口播支持的关系；相关性不能擅自画成因果性。

### 因果回路

- 用于表达自我强化、恶性循环、正反馈或持续改进。
- 骨架：至少 3 个节点，箭头闭合；标出增强、削弱或打断的位置。
- 画面：环形跑道、线团或转盘；小睫毛卡在循环中，或正在剪断一条反馈线。
- 约束：只有确实存在回到起点的影响时才使用闭环，不能把普通流程画成循环。

### PDCA

- 用于计划、执行、检查、调整的持续改进。
- 骨架：Plan → Do → Check → Act → 回到 Plan。
- 画面：四个相连的工作台、四段跑道或一个需要反复修补的机器；小睫毛在 Check 或 Act 处做关键动作。
- 约束：四步必须可区分；如果内容只有一次性流程，不要强行使用 PDCA。

## 选择与优先级

### 决策树

- 用于根据条件、判断或限制选择不同路径和行动。
- 骨架：问题 → 2-4 个判断门 → 分支结果 / 下一步行动。
- 画面：岔路、门、闸机或分流水管；小睫毛根据条件开门，不把所有选项排成目录。
- 约束：每个分支必须对应不同条件或行动；没有判断条件时改用对比或列表。

### 2×2 矩阵

- 用于两个明确维度下的分类、优先级或策略选择。
- 骨架：横轴 + 纵轴 + 四个区域 + 3-6 个对象；至少突出一个比较结论。
- 画面：手绘坐标纸、两条绳子或四个地块；小睫毛把对象搬到象限并解释边界。
- 约束：两个轴必须写清；没有两个可比较维度时，不使用矩阵。

### SWOT

- 用于按内部/外部和有利/不利整理一个对象的条件。
- 骨架：Strengths / Weaknesses / Opportunities / Threats 四区。
- 画面：四个房间、四个抽屉或一张被分成四块的桌面；小睫毛把信息卡放入对应区域。
- 约束：不擅自判断企业事实；只呈现用户材料中的条件，缺失项可以标记“待验证”。

## 概念与方法

### Why–What–How

- 用于解释一个方法为什么重要、它是什么、如何使用。
- 骨架：Why 目的 / 问题 → What 定义 / 组成 → How 步骤 / 行动。
- 画面：三层抽屉、三扇门或从动机到工具再到动作的阶梯；小睫毛依次打开三层。
- 约束：How 必须落到动作，不要只写抽象口号。

### 分层模型

- 用于表达从抽象到具体、从基础到上层、从输入到结果的组成关系。
- 骨架：3-5 层，每层一个短语；说明层与层之间是支撑、包含还是递进。
- 画面：阶梯、地层、抽屉或纸盒；小睫毛搭建、搬运或修补关键层。
- 约束：不要默认画成金字塔；层级方向和关系必须由内容决定。

### 系统关系图

- 用于表达角色、模块、资源、阻力和反馈如何共同影响一个结果。
- 骨架：3-6 个核心节点，标出输入、输出、影响或反馈；删除不影响结论的节点。
- 画面：低科技机器、线团、管道或一张被角色共同操作的白板；小睫毛连接关键节点。
- 约束：不是软件架构图；不堆模块、不画无意义双向箭头。

## 时间与体验

### 用户旅程 / 时间线

- 用于表达阶段、触点、情绪或关键转折如何随时间变化。
- 骨架：3-6 个阶段，阶段之间有顺序；每个阶段只有一个主要动作或判断。
- 画面：弯曲路线、车站、里程碑或连续房门；小睫毛在关键转折处停下、转弯或开门。
- 约束：如果重点是数量变化，改用折线图；如果重点是动作顺序，使用流程图。

## 输出前的选择顺序

1. 先问：观众需要看懂数量、逻辑、因果、选择、阶段还是组成？
2. 数量关系用图表；逻辑关系用模型；动作顺序用流程；真实经历用小漫画或用户旅程。
3. 在候选模型中选最小结构，并写清唯一认知任务、节点关系和阅读路径。
4. 如果一个模型无法承载全部内容，拆成“总览 + 局部”，不要增加节点密度。
5. 生成后检查模型结构是否成立，再检查小Gecko的动作和手绘风格。
